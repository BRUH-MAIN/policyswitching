## How git auth actually works on the laptop (for reference)

`gh` CLI, logged in as RohanRamesh21, token in the OS keyring, wired into git
by `gh auth setup-git` — which writes
`credential.https://github.com.helper = !/usr/bin/gh auth git-credential`
into `~/.gitconfig`. No `~/.git-credentials`, no `~/.netrc`, no SSH keys, no
`GH_TOKEN`/`GITHUB_TOKEN` in the environment. Nothing here is copyable to the
cluster: the token is keyring-resident and account-wide, and shouldn't be
reused on a shared filesystem regardless.

**Recommended for the cluster (needs a user action on the GitHub account, so
not done from here):** an SSH deploy key scoped to this one repo —
`ssh-keygen -t ed25519 -f ~/.ssh/policyswitching_deploy -N ""` on the cluster,
add the `.pub` as a **write-access** deploy key on BRUH-MAIN/policyswitching,
then `git remote set-url origin git@github.com:BRUH-MAIN/policyswitching.git`
(add a `Host github.com / Hostname ssh.github.com / Port 443` block if
outbound 22 is blocked). Fallback: `gh auth login --hostname github.com
--git-protocol https` works headless via the device-code flow, but with no
keyring on a compute node gh stores the token in plaintext at
`~/.config/gh/hosts.yml`, which on `/dist_home` is worse than the deploy key.
Avoid a PAT embedded in the remote URL — it persists in `.git/config`.
